      GitHub corner · skill 3 of 9

      Issues as a lab notebook

      An issue isn't only a bug report. For bring-up it was our lab notebook: a checklist to work through and a dated log of every finding. Worked example: issue #3, "Verify hardware assumptions on a real Core2 v1.3".

      Task lists
      Lines starting - [ ] become checkboxes; - [x] is ticked. GitHub shows the progress on the issue (and wherever it's linked).
      Comments as a log
      Each finding went in as a new comment, so the issue reads top to bottom as what happened, in order, with timestamps.
      Refs vs Closes
      "Refs #3" in a commit or PR links to the issue and leaves it open. "Closes #3" closes it when the PR merges. Use Closes only when the work is truly finished.
      Labels and milestones
      Issue #3 carries the firmware label and sits in the "Stage 4: Hardware bring-up" milestone, so it shows up in both views.
      Closing with a summary
      Before closing, leave a last comment: what was confirmed, what moved elsewhere (face-down waits for the napping baby). Future you will read that first.
